## Vocabulary

Semantics classes:

- `implemented`: the control reaches the backend or transport with the documented effect
- `ignored`: accepted by the schema or transport but never read on that path (including a client disconnect that no cancellation observes)
- `rejected`: refused explicitly (400/422/409/499 or a schema Literal admitting one value) instead of being approximated
- `rejected-in-job`: accepted by the schema and answered 202 by a job route, then refused explicitly inside the job thread: the refusal surfaces only as job record status failed with the error string on GET /api/jobs/{identifier} (jobs.py:210, :177); no HTTP status or error code reaches the caller
- `declared-only`: named by a document, capability record, docstring or field, but no code path provides it

Semantics origins (the `origin` of every row in the JSON):

- `table`: an explicit SEMANTICS row of the generator
- `derived`: emitted for every operation whose JSON request model declares the field (DERIVED_FIELD_SEMANTICS)
- `shared`: copied from the operation named in shared_from, whose handler this operation runs with the qualifier prefixed to the control (SHARED_SEMANTICS)

Auth classes (src/titanos/server.py Guard with src/titanos/broker/auth.py):

- `public`: exact path in the per-app public set (server.PUBLIC_ROUTES; GET /api/version joins it in managed role only): GET only (405 otherwise), a declared body is refused 400, no credential, no scope, no keyless cross-site check, not tracked by the registry gate
- `scoped`: a principal is required and its scope is checked by the Guard before the body is read (src/titanos/broker/auth.py Authenticator with broker.scopes.required_scope; the row field `scope` is the required scope from broker.scopes.ROUTE_SCOPES, per action where a surface decides it; where a provider row of the native passthrough shares the shape and answers some requests (OpenAI /v1/videos: a cloud model in the body, or a video id created through Titanos by the caller), the Guard accepts `scope` or native, and BrokerDispatch still requires `scope` when the Titanos route answers). Keys enforced (a bootstrap TITANOS_API_KEY or any record in keys.json): no credential or a wrong one is 401, a principal without the scope is 403 scope_denied, and the credential headers are Authorization: Bearer plus the family vendor header named in the row field `credential_headers`. Keyless loopback mode: the anonymous loopback principal holds broker.scopes.ANONYMOUS_LOOPBACK_SCOPES (key and credential writes answer 403 keyless_mode_refused), cross-site browser requests are refused 403, and a non-loopback bind with nothing enforced answers 401. The registry gate answers 503 registry_reloading/registry_unavailable

Scope rules: admin covers every scope; inference covers inference:*; cloud covers cloud:<upstream_id> but not cloud:store; broker:admin covers broker:read; models:write covers models:read; a value a|b is satisfied by either scope; authenticated is satisfied by any principal (never granted); a route missing from ROUTE_SCOPES needs admin (fail closed). ## Shared semantics

Operations whose handler runs another operation's code path carry that operation's semantics rows too, prefixed with the qualifier (`origin` shared, `shared_from` names the source).

- **POST `/api/jobs`** with `task=music` runs the 30 semantics rows of `POST /v1/music/generations` (listed below as `task=music: <control>`): POST /v1/music/generations wraps MusicRequest into MusicJob and calls the POST /api/jobs handler (server.py:2262); MusicJob is the task=music member of the AssetJob union with the same fields, so CLI music, Client.submit_music and MCP submit_job reach every music control through POST /api/jobs
