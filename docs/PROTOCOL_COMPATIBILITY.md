# HTTP protocol compatibility

Titanos keeps one local inference implementation behind several wire formats. The extended media routes reuse HiveMind HLI's route names where both projects implement an operation; [API_PLUS.md](API_PLUS.md) records the implemented subset, and `GET /v1/extensions` and `/openapi.json` provide discoverable schemas. The complete route list with one-line purposes is [INTERFACES.md](INTERFACES.md).

| Client family | Implemented routes | Boundary |
|---|---|---|
| OpenAI shapes | models, chat/completions, completions, embeddings, speech, transcription, image generation/edit, video jobs; `/v1/moderations` through a cloud upstream only | Listed operations; not the entire hosted platform |
| Responses | `/v1/responses`; `/v1/responses/{id}` retrieve, delete, cancel and input items for responses stored at a cloud upstream | Stateless text/image output over local chat/vision backends; native llama.cpp passthrough retains its additional capabilities (function tools, `tool_choice`, `parallel_tool_calls`, `function_call`/`function_call_output` items and their streaming events, completed with the sequence numbers, output/content indexes and full `response.created` object the stock OpenAI SDK's `responses.stream()` helper requires; see [Agent frameworks on local models](#agent-frameworks-on-local-models)), and on the in-process backends those fields are refused with a 400 naming the model's backend and the missing capability. No local stored conversation service; a response stored at an OpenAI upstream (key scope `cloud:store` and the upstream's `allow_store`) is reachable only by the key that created it; see [RESPONSES.md](RESPONSES.md). |
| Extended (HLI-compatible names) | `/v1/translations`, `/v1/audio/translations`, `/v1/images/ocr`, `/v1/images/detect`, `/v1/images/depth`, `/v1/images/segment`, `/v1/sentiment`, `/v1/sentiment/compose`, `/v1/rerank`, `/v1/retrieval/answer`, `/v1/classifications/text-pairs`, `/v1/audio/vad`, `/v1/audio/diarizations`, `/v1/audio/analysis`, `/v1/extensions` and `/v1/extensions/infer` | Registered compatible local checkpoints; no synthetic success for missing modalities; see [API_PLUS.md](API_PLUS.md) |
| Ollama shapes | `/api/version`, `/api/tags`, `/api/ps`, `/api/show`, `/api/chat`, `/api/generate`, `/api/embed`, `/api/embeddings`; typed refusals on `/api/pull`, `/api/create`, `/api/copy`, `/api/delete` | JSON and real NDJSON text streaming; supported sampling options only. `/api/tags` returns `name`, `model`, `details.format` (the Titanos backend), `details.family` (the Titanos task) and a `titanos` object (`task`, `device`), without Ollama's `size`, `digest` or `modified_at`; `/api/ps` returns Titanos catalog rows (`id`, `object`, `created`, `owned_by`, `task`, `status`) with Ollama's `name` and `model` set to the id, without `size`/`digest`/`expires_at`/`size_vram`, and lists loaded Python-engine and native llama.cpp models. `/api/version` answers `{name, version, role}` in every role (public only in managed role). `/api/show` is built from the registry and the passive model inspection and never loads: `details.format`/`details.family` as on `/api/tags`, `parameters` (`num_ctx` from `native.context_size`, registration defaults), `model_info` (`titanos.*`, `llama-cpp.*`, `general.architecture` when `config.json` names it), `capabilities` and `titanos.setup`, without a Modelfile, template, license, size or digest (`verbose` is accepted and named in `X-Titanos-Ignored`). `/api/pull`, `/api/create`, `/api/copy` and `/api/delete` answer 400 `unsupported_capability` with `param` naming the field and a message naming Titanos's acquisition path (`/api/model-providers`, `/api/acquisitions`, `/api/models/register`, `DELETE /api/models/registrations/{name}`); nothing is downloaded, copied or deleted. `/api/push` and `/api/blobs/*` are absent. |
| Anthropic shapes | `/v1/messages` | Text (base64 image) input, normal text streaming, native function calls on llama.cpp models nonstreaming and streaming (`tool_use` content blocks with `input_json_delta` fragments and `stop_reason: tool_use`; `tool_choice.disable_parallel_tool_use` maps to `parallel_tool_calls: false`; see [Agent frameworks on local models](#agent-frameworks-on-local-models)). `/v1/messages/count_tokens` counts with the model's own template and tokenizer on llama.cpp models (400 on other local backends). On local models `metadata`, `thinking`, `service_tier`, `inference_geo`, `context_management` and `output_config` without `format` are accepted, ignored and named in the `X-Titanos-Ignored` response header ([below](#agent-harness-fields-on-the-local-routes)), `container` and `output_config.format` are refused (400), and `betas`, `mcp_servers` and `output_format` are refused (422); `document`/`thinking`/`server_tool_use` blocks and URL or file image sources are refused (400), and tools on non-native models are refused with a 400 that names the model, its backend and the missing capability; malformed blocks are 400 client errors; `stop_reason` is never `stop_sequence`. `x-api-key` is accepted as the Titanos key on `/v1/messages*` and `/v1/models*` (as well as `Authorization: Bearer`); `anthropic-version` is not read for local models (on `/v1/models` it selects Anthropic's list shape). |
| ElevenLabs shapes | `/v1/text-to-speech/{voice_id}` | Local registered voice/model, WAV only: `output_format` may be omitted or `wav` (upstream mp3/pcm/ulaw/alaw/opus values are refused, 400); the body allows only `text` and `model_id` (a Titanos registered model name; omit it only when exactly one speech model is registered), `voice_id` is a Titanos voice alias, `voice_settings` and every other upstream field are refused (400); errors of local models use the OpenAI-style envelope; `xi-api-key` is accepted as the Titanos key on the ElevenLabs routes (as well as `Authorization: Bearer`). `/v1/text-to-speech/{voice_id}/stream` answers with the same local WAV handler, `/v1/speech-to-text` is answered by a local transcription model, and `/v1/voices` and `/v1/voices/{voice_id}` list local voices; `/with-timestamps`, websocket, `/v1/user*` and `/v1/history` have no local implementation (with a broker ElevenLabs upstream they reach the provider through the native passthrough). |
| Gemini shapes | `/v1beta/models`, `/v1beta/models/{model}`, `/v1beta/models/{model}:generateContent`, `:streamGenerateContent`, `:embedContent`, `:batchEmbedContents`, `:countTokens` | Local chat and embedding models are answered by re-encoding the request for the local OpenAI routes; streaming needs `alt=sse`; `x-goog-api-key` is accepted as the Titanos key; a `?key=` query credential is refused (401 `query_credential_refused`). |
| MCP | `/mcp/` and stdio | Official SDK, typed tools, resources and prompts; see [MCP.md](MCP.md) |

The rows above describe local models, whose strict request schemas are unchanged. When the operator configures the optional [cloud broker](BROKER.md), the same routes can be served by cloud upstreams: on passthrough (the upstream speaks the route's own protocol) the provider's native request fields are accepted and forwarded, and on translated paths every field goes through the profile's parameter map (mapped, dropped with a note, or refused with 400). Broker errors use each route's native envelope, and translated requests name the fields they dropped in the `X-Titanos-Dropped` response header. With the broker, provider endpoints that no Titanos route covers (files, batches, voices, music, Interactions, the OpenAI Realtime, Gemini Live and ElevenLabs stream-input WebSockets and more) are reachable through the guarded native passthrough: `/native/<upstream>/<path>`, or the provider's own path when exactly one visible upstream offers it, so an unmodified OpenAI, Anthropic, Gemini or ElevenLabs SDK pointed at Titanos keeps working (the `native` scope; the vendor key headers `x-api-key`, `xi-api-key` and `x-goog-api-key` are accepted on those paths). Plain provider model ids (`gpt-4o-mini`, `claude-opus-5-5`, `gemini-2.5-flash`, `eleven_multilingual_v2`) resolve on the OpenAI, Anthropic, Gemini and ElevenLabs routes when one visible upstream of that provider lists them and no local model, alias or virtual model has the name; an Anthropic client's `GET /v1/models` (with `anthropic-version`) and an ElevenLabs client's (with `xi-api-key` and no `Authorization`) get their own list shapes; `/v1/rerank` also serves cloud rerankers. What each provider serves with a key, endpoint by endpoint, is in [BROKER.md](BROKER.md#what-works-with-a-key). The per-adapter field behaviour is in the broker sections of [PROTOCOL_DEVIATIONS.md](PROTOCOL_DEVIATIONS.md) and the evidence per surface in [BROKER_MATRIX.md](BROKER_MATRIX.md).

Ollama's `num_predict` maps to `max_tokens`. Temperature, top_p, top_k, min_p, repeat_penalty, seed and stop use the same inference controls, with Titanos bounds: `seed` must be 0..2^32-1 (400 otherwise) and `seed: 0` is a fixed seed rather than Ollama's unset meaning; `stop` is bounded by `TITANOS_MAX_STOP_SEQUENCES`/`TITANOS_MAX_STOP_CHARS` (400). `keep_alive` is accepted on `/api/chat`, `/api/generate`, `/api/embed` and `/api/embeddings`: `0` unloads the model after the answer (the `POST /api/models/unload` operation, best effort when another request holds it), a negative value keeps it resident (Titanos's default), a positive duration has no Titanos idle timer and is named in the `X-Titanos-Dropped` response header, and a wrong type or an unparseable duration is 400. `options.num_ctx` is accepted: on a llama-cpp model it sizes the per-slot context of the runtime (started, or restarted once idle, at the next power of two up to the largest per-slot context; [NATIVE.md](NATIVE.md)) and is refused with 400 `context_limit` above that largest context (`/v1/chat/completions` names it instead); the other backends have no context option (the checkpoint's own length bounds prompt plus `max_tokens`), so it is named in `X-Titanos-Dropped`. The other unknown top-level and `options` fields (`think`, `raw`, `context`, `suffix`, `template`, `num_gpu`, mirostat, ...) are refused: 422 on `/api/chat` and `/api/generate`, 400 on the manually parsed `/api/embed`/`/api/embeddings`; hardware/load options, model installation, cloud routing and thinking protocols are never silently approximated; use Titanos's explicit model configuration and lifecycle API. `/api/generate` is raw-mode: the prompt is not rendered through the model chat template and `system` is prepended with a newline. Ollama tool loops complete in Ollama's own shape on llama-cpp models: the assistant `tool_calls` Titanos returns carry no id, and a tool-result turn (`role: tool` with `tool_name`, no `tool_call_id`) is bound to the pending tool call with that `tool_name` (the next unanswered call when `tool_name` is absent) before it reaches the engine; a tool result with no preceding tool call to answer is a 400 naming the message. A `tool_call_id` given explicitly is used as on the OpenAI route. With `stream: true` the argument fragments llama.cpp streams are gathered into whole `tool_calls` with object arguments and emitted in one frame ahead of the final frame, so a stock client that validates every frame completes the loop streaming too. Top-level `images` is refused on both routes; per-message images inside `/api/chat` are mapped (always labelled `image/png`). `/api/embed` defaults `truncate` to `TITANOS_EMBEDDING_TRUNCATE` (false) where Ollama defaults to true; both embedding routes accept `user` (and a null `dimensions`) and name them in `X-Titanos-Ignored` as `/v1/embeddings` does. Response gaps: `load_duration`, `prompt_eval_duration`, `eval_duration`, generate `context` and `message.thinking` are not emitted; `done_reason` may be `tool_calls`. With a configured API key every `/api/*` route requires `Authorization: Bearer`, which stock Ollama clients do not send; in keyless loopback mode the stock `ollama` Python client works as is (`tests/check_ollama_sdk.py` runs it against a real `titanos serve`). A request that names a cloud model through `/api/chat`, `/api/generate` or `/api/embed` is answered by the broker; the strict local refusals above apply to local models only. Token usage in streaming protocols is reported when the backend supplies it. The complete per-field map is [PROTOCOL_DEVIATIONS.md](PROTOCOL_DEVIATIONS.md), generated from `protocol_deviations.json` and asserted by `tests/check_protocol_deviations.py`.

`POST /v1/videos` accepts multipart fields (the HLI/OpenAI convention) or the equivalent JSON. Specify model, prompt, size and either frames/fps or seconds. Jobs have persistent state and separate content retrieval. Text-conditioned and image-reference video are implemented for compatible Diffusers checkpoints. Supply an inline input_reference image data URL in JSON or a multipart image/reference upload. The loaded pipeline must support image conditioning; unsupported capabilities and controls fail explicitly. Code support and model/package qualification remain separate. Deleting an active video requires cancellation and a terminal state first; deleting a completed record makes it unavailable without replaying inference.

Nonstreaming VAD (`/v1/audio/vad`), speaker diarization (`/v1/audio/diarizations`), overlap-preserving audio analysis (`/v1/audio/analysis`) and music generation (`/v1/music/generations`) are implemented typed local operations whose model/hardware qualification is recorded per row in [current capability status](CAPABILITY_MATRIX.md). A complete combined super-transcription, speaker enrollment, 3D generation, moderation, remote provider accounts, training, and full hosted-provider state are not claimed by these adapters. Unknown request fields are refused everywhere: 422 by schema on JSON routes (the identity, cache, storage and reasoning hints agent harnesses send, such as `user`, `metadata`, `store: false`, `prompt_cache_key` and `reasoning_effort`, are accepted, ignored and named in the `X-Titanos-Ignored` response header on the chat, Responses and Messages routes; see [below](#agent-harness-fields-on-the-local-routes). The Ollama `options` object HiveMind's gateway adds to every chat request it sends a non-cloud backend (`{"num_ctx": N}`) is accepted on `/v1/chat/completions` and `/v1/completions` too, never a 422: `options.num_ctx` is a foreign extension there, so on a llama-cpp model it sizes the runtime up to the largest per-slot context ([NATIVE.md](NATIVE.md)) and nothing is named, and above that, or on the other backends, which have no context option, it is not honoured and named in `X-Titanos-Ignored`; `/api/chat` keeps its 400 `context_limit` above the largest per-slot context because there `num_ctx` is a native field the client expects honoured; the prompt itself stays bounded by the engine's own context check; every other `options` key is named there as `options.<key>` and never applied; a non-object `options` or a non-positive-integer `num_ctx` is a typed 400), 400 `unsupported_capability` naming the fields on the multipart routes (`/v1/audio/transcriptions`, `/v1/audio/translations`, `/v1/images/edits`). Future operations get explicit names and schemas under the extensions interface and corresponding MCP tools. A broad interface is not a universal architecture loader.

Use `GET /api/info`, `/v1/models`, `/api/models/capabilities` and `/v1/extensions` to choose supported work. Capability presence describes code/configuration; the validation report supplies model/hardware execution evidence. The per-operation binding of every route to its request/response models, auth class, MCP tools, CLI subcommands, Python client methods and the implemented/ignored/rejected/rejected-in-job/declared-only status of its declared controls is [ROUTE_CONTRACT_MATRIX.md](ROUTE_CONTRACT_MATRIX.md), generated in-process from the OpenAPI schema, the MCP registry and the source by `tools/build_route_contract_matrix.py` and asserted as a fixed point by `tests/check_route_contract_matrix.py`.

## Agent frameworks on local models

Tool calling, tool-call history and structured output reach a model only on the llama-cpp native backend: the llama.cpp server renders the model's own tool template, parses its tool calls and applies the JSON-schema grammars. Titanos forwards those requests unchanged on the OpenAI chat and Responses routes and translates the Anthropic Messages shape to and from them, nonstreaming and streaming (`tool_use` content blocks with `input_json_delta` fragments, `stop_reason: tool_use`). On the in-process backends (transformers, openvino-genai, onnx, ...) a request that needs one of those capabilities is refused before inference with `400 unsupported_capability` whose message names the model, its backend, the missing capability and the route the client used, for example `Model 'assistant' runs on the transformers backend, which does not implement tool calling (tools) on /v1/chat/completions; register a llama-cpp (GGUF) model for tool calling, tool-call history and structured output`; nothing is dropped silently. `tests/check_agent_tools.py` (contract job) asserts the translation and the refusals over a synthetic native seam.

Observed against a real `titanos serve` with the llama.cpp b10809 CPU binary and Qwen2.5-0.5B-Instruct (q4_k_m GGUF, `device: cpu`, `gpu_layers: 0`) by `tests/check_agent_loops.py` (manual tier: `--llama-server`, `--gguf`, `--sdk-python`; openai 3.24.0, anthropic 1.11.0, openai-agents 0.23.1) on 2026-10-05; every case ran its complete loop against the loopback serve with a placeholder key and no hosted API:

| Client | Loop | Result |
|---|---|---|
| OpenAI SDK | `chat.completions`: tools -> `tool_calls` -> `role: tool` -> text, nonstreaming and streaming (incremental `tool_calls` arguments reconstruct valid JSON); `tool_choice: {type: function}` and `parallel_tool_calls` true and false accepted with no `X-Titanos-Ignored` or `X-Titanos-Dropped` header; `response_format: json_schema` answers valid JSON of the schema | works |
| OpenAI SDK | `responses.create`: tools -> `function_call` -> `function_call_output` -> message, nonstreaming and streaming (`response.output_item.added`, `response.function_call_arguments.delta`, `response.output_item.done`, `response.completed`) | works |
| Anthropic SDK | `messages.create`: tools -> `tool_use` -> `tool_result` -> text with `stop_reason: tool_use`; `messages.stream()`: the `tool_use` block is built from `input_json_delta` and `get_final_message()` carries the parsed input | works; anthropic 1.x has no `temperature` keyword on `messages.create`, so sampling travels in `extra_body` |
| openai-agents | `Agent` with a `function_tool`, `Runner.run` over `OpenAIChatCompletionsModel` and over `OpenAIResponsesModel` (the framework's default path), tracing disabled | works (`ToolCallItem`, `ToolCallOutputItem`, `MessageOutputItem`); see the caveats |

Caveats from the same run, all backend or model behaviour that Titanos forwards unchanged:

- With a system message in the prompt (an `Agent(instructions=...)`), llama.cpp b10809 with the Qwen2.5-0.5B template answered text to `tool_choice: auto` and `required` alike; the same request without a system message calls the tool. The lane runs the framework agent with `instructions=None` and `tool_choice: required` for the first turn (the framework resets it to `auto` after a tool call).
- With `tool_choice: auto` the 0.5B model does not always call the tool; whether it does and whether the city is right is reported as model quality, separately from the engine result.
- The llama.cpp `/v1/responses` route accepted `text.format: json_schema` but did not constrain the output in this probe (fenced JSON text); `response_format: json_schema` on `/v1/chat/completions` did. Use the chat route for grammar-constrained structured output.
- Tool `strict`, `type` and `cache_control` are not forwarded by the Anthropic translation; `message_start` reports `usage` as `0/0` and the real counts arrive in `message_delta`.

## Agent-harness fields on the local routes

Agent harnesses (Claude Code, Codex) and the routers in front of them send identity, cache and storage hints that local
models have no use for. The local routes accept these fields, ignore them and name them in the `X-Titanos-Ignored`
response header (nothing is dropped silently):

| Route | Accepted and ignored | Typed 400 `unsupported_capability` |
|---|---|---|
| `POST /v1/chat/completions` | `metadata`, `user`, `store: false`, `prompt_cache_key`, `prompt_cache_retention`, `safety_identifier`, `service_tier`, `reasoning_effort`, `verbosity` (`top_logprobs` is a schema field: honoured on llama-cpp models, `0` is served, a live value on an in-process backend is a typed 400; see [OPTION_PARITY.md](OPTION_PARITY.md)) | `store: true` |
| `POST /v1/responses` | `include`, `reasoning`, `truncation`, `user`, `prompt_cache_key`, `prompt_cache_retention`, `safety_identifier`, `service_tier`, `top_logprobs`, `text.verbosity` (`store: false` and `metadata` are part of the schema) | `store: true`, `previous_response_id`, `background: true` |
| `POST /v1/messages` | `metadata`, `service_tier`, `thinking`, `inference_geo`, `cache_control`, `context_management`, `output_config` without `format` (block-level `cache_control` is ignored as before) | `container`, `output_config.format` |

Any other unknown field still answers 422, as before (except on a managed instance with `TITANOS_UNKNOWN_FIELDS=ignore`,
which names it in `X-Titanos-Ignored` on the chat and responses routes; [TOPOLOGY_ROLES.md](TOPOLOGY_ROLES.md)). Brokered
cloud refs pass every field through to the provider. Anthropic `count_tokens` on a local target works for llama-cpp
models only. `tests/check_broker_local_compat.py` asserts the table.

## Chat without loading a model

Send the literal boolean `require_loaded: true` to `POST /v1/chat/completions`
to use only a currently usable, already-loaded matching model/worker:

```json
{"model":"assistant","messages":[{"role":"user","content":"Hello"}],"require_loaded":true,"stream":true}
```

A registered cold, wrong-resident or missing-runtime target returns HTTP 409
with `error.code: "model_not_loaded"` before successful response headers.
Existing validation, authentication, queue, unavailable-worker and cancellation
errors retain their meanings. Busy warm workers use the existing bounded queue;
an explicitly requested worker is never substituted. This request never initiates
Titanos-managed model loading, process startup, repair, cold fallback or replay.

Admission is checked under the existing model ownership lock/reservation. Ordinary
unload/replacement cannot intervene through execution and ASGI response cleanup;
native unload retains its HTTP 409 `model_busy` response while reserved. A slow
client therefore holds the selected slot longer. Disconnect cancellation remains
cooperative. Provider/OS failure or explicitly owned shutdown can interrupt work,
and backend-internal paging, allocation, context preparation or compilation may
still occur. An earlier inventory snapshot is not a reservation or checkpoint pin.

Omitted or false preserves lazy loading. The field is not inherited from model
defaults, has no environment/header alias and is removed before provider requests.
MCP `chat` and Python `Client.chat(..., require_loaded=True)` reach the same route.
Other public routes do not accept or advertise this revision's guarantee.

Discover support in `/api/info` at
`inference_contracts.require_loaded = {"revision":1,"routes":["/v1/chat/completions"]}`.
A strict consumer must check the supported revision and route, force true, and
refuse missing/unsupported capability rather than retrying without the flag.
This handshake describes the request contract; it is not model/hardware qualification.
